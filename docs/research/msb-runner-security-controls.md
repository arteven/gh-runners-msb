## Short answers

| Question | Local Backend | Remote Backend |
|---|---|---|
| **Default egress** (no `WithNetwork`) | Public internet plus gateway DNS. Private ranges, loopback, link-local, `169.254.169.254` and the host are denied. Ingress only via published ports. | **Not documented.** The SDK sends `policy: null` and "the hosting driver selects" the deployment profile. The docs' defaults are written as universal, but nothing says the cloud applies them. |
| **Custom egress policy from Go** | Yes. `WithNetwork(&NetworkConfig{DefaultEgress, Rules})`. Rules match groups (`public`, `private`, `loopback`, `link-local`, `metadata`, `host`, `multicast`), IPs, CIDRs, domains, domain suffixes, protocol and port. First match wins. | Yes. `policy` and `strict` travel in the create body. DNS settings, TLS settings, rate limits, NAT64 prefixes, published ports, outbound proxies and custom HTTP deny responses are local-only; most are rejected client-side. |
| **Block metadata / link-local** | Blocked by default. With allow-by-default egress, add a `metadata` deny rule. | Same rule syntax is accepted. Whether a metadata service exists on the cloud worker is **unknown**. |
| **Domain allowlist for HTTPS** | Strict mode (on by default) denies HTTPS allowed *only* by a hostname rule unless TLS interception is on. Interception adds an msb CA to the guest trust store. `DisableStrict: true` falls back to SNI plus DNS-pin matching. | Interception can't be turned on by itself (only together with secrets), so a hostname allowlist needs `DisableStrict: true` **(inferred)**. |
| **DNS controls** | Gateway intercepts UDP/TCP 53; public resolvers by default; rebind protection on by default; `DenyDomains`, custom nameservers, query timeout. | Custom nameservers are rejected. Other DNS settings have no field in the cloud wire type, so they are not applied **(inferred)**. |
| **Runner-to-Runner and Runner-to-host isolation** | Each sandbox is its own VM, own host process, own gateway; sandboxes "can't see or reach one another" without a shared volume or published port. The host group is denied by default. | On cloud the `host` group is the cloud worker. Tenant isolation is not documented. |
| **JIT config: other channels** | `WithEnv` (persisted in the local catalog and returned by `config()`), `WithExecEnv`, exec args, `FS().Write`/`WithPatches` (lands on the writable layer on disk), `WithSecrets` (unusable: the runner signs with the key inside the guest). | Same options. Sandbox env is stored by the cloud and returned in the spec. Stdin, args and files all cross the cloud API. |
| **Where stdin is visible** | Not on any host argv and not in `exec.log` (which captures stdout/stderr only). Lives in the Pool's memory, the per-sandbox process relay and the guest. | Crosses the cloud API. Cloud-side logging of exec input is **unknown**. |
| **Pull by digest** | Yes. `WithImage("…@sha256:…")`; msb fails with `DigestMismatch` if the fetched manifest digest differs, and checks each layer against the config's `diff_ids`. | The reference is passed to the cloud verbatim; it pulls server-side. Verification there is **(inferred)** to be the same code. |
| **Signature / attestation check in msb** | **None.** msb skips attestation manifests in an index; it never verifies signatures. | Same. |
| **Verify at Pool start without new deps** | Yes **(inferred)**: resolve `:1` to its index digest with net/http against GHCR (anonymous token), run `gh attestation verify oci://…@sha256:… --repo arteven/gh-runners-msb --signer-workflow …` (gh is always present for a gh extension), then create Runners from `…@sha256:…`. | Same flow; the digest-pinned reference goes to the cloud. |
| **GitHub on public repos** | "Self-hosted runners should almost never be used for public repositories." Fork PRs run on the Runner once approved or when the author is exempt; this repo is public with the default `first_time_contributors` policy. | Same. |

## 1. Network

### 1.1 Defaults

- **Docs, Backend-neutral.** "Sandboxes can reach the public internet by default. Private networks, the host, loopback, link-local addresses, and cloud metadata endpoints are blocked. Inbound traffic needs a published port." (`M/docs/networking/overview.mdx:12`). The security chapter lists what's denied: RFC 1918, CGNAT `100.64.0.0/10`, ULA `fc00::/7`, loopback, `169.254.0.0/16` and `fe80::/10`, `169.254.169.254` ("takes precedence over link-local"), and "the per-sandbox gateway, meaning your host" (`M/docs/security/network.mdx:15-28`). NAT64-translated metadata and private addresses are treated the same (`M/docs/security/network.mdx:93`).
- **Code, local.** The runtime's `NetworkConfig.policy` is not optional and defaults to `NetworkPolicy::default()` (`M/crates/network/lib/model/config/types.rs:72-74,337-343`), which is `from_profiles([Public])` (`M/crates/network/lib/model/policy/types.rs:1011-1015`). The Go SDK only sends a network block when `WithNetwork` was called (`M/sdk/go/core/sandbox.go:289`).
- **Remote.** The cloud wire type has `policy: Option<NetworkPolicy>` (`M/packages/microsandbox-types/rust/lib/cloud/specs.rs:682-706`), and without `WithNetwork` the SDK sends `policy: null`. "Managed cloud requests do not carry a deployment profile; the hosting driver selects it." and "Cloud chooses its own profile." (`M/docs/networking/overview.mdx:64,115`). The `multi-tenant` profile "enforces public-network access" and "traffic must pass both the platform's public-network policy and the sandbox's policy" (`M/docs/networking/overview.mdx:64,111`). **(inferred)** The cloud most likely runs `multi-tenant` with at least the public-only default, but no source says so.
- **Deployment profile, local.** Local sandboxes default to `single-tenant`; `WithDeploymentProfile(DeploymentProfileMultiTenant)` adds forced public-only access, forced rebind protection, a 1,024 TCP / UDP connection default and no published ports (`M/docs/networking/overview.mdx:62-115,121-128`). An operator can force it in `~/.microsandbox/config.json` (`M/docs/networking/overview.mdx:115`).

### 1.2 What the Go SDK can set

- `NetworkConfig` (`M/sdk/go/core/options.go:1190-1268`): `Rules`, `DefaultEgress` (comment: "Defaults to deny"), `DefaultIngress`, `DenyDomains`, `DenyDomainSuffixes`, `DNS` (`RebindProtection` default true, `Nameservers`, `QueryTimeoutMs`), `TLS`, `DisableStrict`, ports, connection caps, `RateLimiter`, `TrustHostCAs`, `HTTP` deny responses.
- `PolicyRule.Destination` accepts `"*"`, `loopback`, `private`, `link-local`, `metadata`, `multicast`, `public`, `host`, an IP, a CIDR, a domain suffix or a domain, plus `Protocol(s)` and `Port(s)` (`M/sdk/go/core/options.go:1340-1357`). `Rule.AllowDNS()` allows gateway UDP/TCP 53 (`M/sdk/go/core/options.go:1368-1376`).
- Shortcuts: `NetworkPolicy.None()`, `NetworkPolicy.AllowAll()`, and `NetworkPolicy.FromProfiles(public|private|host)`, which builds deny-by-default egress plus gateway DNS. It also sets `DefaultIngress: allow` (`M/sdk/go/core/options.go:1445-1503`). `WithNetwork(NetworkPolicy.None())` keeps the device but denies everything; the docs also describe disabling the device (`M/docs/networking/overview.mdx:14-58`).
- **Footgun:** in Go, setting `DenyDomains`/`DenyDomainSuffixes` *without* any `Rules`/`DefaultEgress` switches the policy to `default_egress: Allow, default_ingress: Allow` plus the domain denies, preserving "legacy 'full network minus blocked domains' semantics" (`M/sdk/go/native/src/lib.rs:1434-1483`, at 1475). **(inferred)** That would open private ranges, the host and metadata, because the public-only default is replaced.
- **Rate limits** are local only; "Cloud does not support this setting" (`M/docs/networking/overview.mdx:469`).

### 1.3 Hostname allowlists and HTTPS

- "Strict hostname policy mode is enabled by default: hostname allowlists fail closed unless microsandbox can inspect the request authority. … Non-intercepted HTTPS is denied when it would otherwise be allowed only by a hostname rule. … IP, CIDR, group, and default allow rules are not treated as hostname-based allows." (`M/docs/networking/overview.mdx:407`). Go opts out with `NetworkConfig.DisableStrict` (`M/sdk/go/core/options.go:1219-1221`), sent as `strict` (`M/sdk/go/core/sandbox.go:487-488`).
- Even with strict off, domain rules need "a live DNS binding between the allowed name and destination IP", checked against SNI (`M/docs/security/network.mdx:105-115`).
- TLS interception "Adds that CA to the guest's trust store". Apps with their own stores need `msb-trust.sh` (`M/docs/networking/tls.mdx:12-20,97-104`). **(inferred)** For a Runner this means .NET, Node and every Docker container started by a job would have to trust the msb CA. That is impractical, so a GitHub-domain allowlist realistically uses `DisableStrict: true`.
- **Remote:** TLS inspection is marked "not available on our managed cloud" (`M/docs/networking/tls.mdx:8`). The SDK rejects any non-default `network.tls` unless the sandbox has secrets and the TLS config equals the secret helper's default (`M/sdk/rust/lib/context/cloud/sandbox.rs:948-951,1048-1073`). The limitations page: "custom TLS settings are local-only. This does not restrict the default TLS interception flag used by secrets." (`M/docs/cloud/limitations.mdx:18`). `strict` is carried in the cloud body (`M/packages/microsandbox-types/rust/lib/cloud/mod.rs:620-627`).
- **What GitHub requires** for a runner: outbound HTTPS on 443 to `github.com`, `api.github.com`, `*.actions.githubusercontent.com` (essential), plus `codeload.github.com`, `results-receiver.actions.githubusercontent.com`, `*.blob.core.windows.net`, the `objects*.githubusercontent.com` family, `ghcr.io`, `pkg-containers.githubusercontent.com` and others by function. "In addition, your workflow may require access to other network resources." Some names are CNAMEs (`GH:actions/reference/runners/self-hosted-runners`, "Communication"). **(inferred)** Real jobs also pull from npm, Docker Hub and similar, so a GitHub-only allowlist would break most workflows. It fits only as an opt-in.

### 1.4 DNS

- The gateway intercepts UDP/53, TCP/53, and DoT when interception is on; DoH on 443 and tunnelled DNS can't be seen (`M/docs/security/network.mdx:117-121`). Rebind protection rewrites private, loopback and link-local answers to `NXDOMAIN` unless an explicit address rule allows them (`M/docs/security/network.mdx:95-103`). The gateway uses public resolvers by default on current runtimes (`M/docs/networking/overview.mdx:113`).
- **Remote:** "custom nameservers … are local-only" (`M/docs/cloud/limitations.mdx:18`), and the SDK rejects them (`M/sdk/rust/lib/context/cloud/sandbox.rs:706-715`). `CloudNetworkSpec` has only `enabled`, `policy`, `secrets`, `strict` and connection caps. The OpenAPI schema says "Interface overrides, host port mapping, DNS, TLS interception, rate limits, and host-CA trust are not part of this type. Unknown fields are ignored" (`M/packages/microsandbox-types/rust/lib/cloud/specs.rs:682-706`; `M/docs/api-reference/openapi.json`, schema `CloudNetworkSpec`). **(inferred)** `DNS.RebindProtection` and `QueryTimeoutMs` set on a remote Runner are silently not applied. `DenyDomains` survives, because the Go native layer turns it into policy rules.

### 1.5 Isolation between Runners and from the host

- **Local:** "Sandboxes share no kernel, no writable filesystem layer, no network namespace, and no process tree. Each is its own VM in its own host process, with its own per-sandbox network gateway. … Absent that, they can't see or reach one another." (`M/docs/security/isolation.mdx:122-124`). The per-sandbox process runs as the launching user, needing only `/dev/kvm` (`M/docs/security/isolation.mdx:21-26`). The host (`host.microsandbox.internal`) and LAN are denied by default (`M/docs/security/network.mdx:20-30`). Published ports bind to `127.0.0.1` (`M/docs/security/network.mdx:16`); the Pool publishes none.
- **Remote:** "On cloud, the `host` group refers to the cloud worker" (`M/docs/networking/overview.mdx:744`). Compute is "Shared … CPU capacity shared with other sandboxes" (`M/docs/cloud/pricing.mdx:14`). Nothing documents cross-tenant network isolation on the cloud.
- **In-guest:** the default security profile keeps root semantics "including … `sudo`, and Docker-in-Docker". The `restricted` profile "is incompatible with workloads that need those" (`M/docs/security/isolation.mdx:56-64`). The Image contract requires passwordless sudo and `dockerd` (#9), so Runners must use the default profile, and a job is root in its VM **(inferred)**. The VM and the network policy are the only boundaries. **(inferred)** Docker containers inside the Runner reach the network through the same guest `virtio-net`, so the policy covers them too.

### 1.6 Metadata endpoint on remote

Unknown. No microsandbox source names the cloud's hosting provider, and the docs never say whether `169.254.169.254` answers on a cloud worker. If the cloud applies the default or `multi-tenant` policy, it is blocked either way. An explicit `{Action: deny, Destination: "metadata"}` rule (plus `link-local`) costs nothing and is accepted on both Backends (`M/docs/security/network.mdx:43-91`) **(inferred)**.

## 2. Secrets: getting the JIT config into the VM

Context: #7 decided stdin, then `run.sh --jitconfig` inside the guest. GitHub's own example passes it on argv: `./run.sh --jitconfig ${encoded_jit_config}` (`GH:actions/reference/security/secure-use`, "Using just-in-time runners").

| Channel (Go) | Host argv / `ps` | Persisted on host or cloud | Visible through API / `config()` |
|---|---|---|---|
| **Stdin** (`ExecStream` + `WithExecStdinPipe`, `TakeStdin`) | No | Local: no. `exec.log` captures only the primary session's stdout/stderr (`M/crates/runtime/lib/runner/exec_log.rs:1-17`). Remote: **unknown** | No **(inferred)** |
| **Exec args** (`run.sh --jitconfig X`) | No: sent over the agent channel, not the sandbox process argv **(inferred)** | Local: not for attached exec **(inferred)**. A *detached startup command* is persisted and its args are traced (`M/crates/runtime/lib/runner/vm.rs:1626-1627`; `M/docs/changelog/2026-06-26.mdx:82`). Remote: unknown | No |
| **Exec env** (`WithExecEnv`, `M/sdk/go/core/options.go:1719`) | No | Same as exec args **(inferred)** | No |
| **Sandbox env** (`WithEnv`, `M/sdk/go/core/options.go:780`) | No. Secret-bearing env goes over an anonymous config fd, "off `ps` / `/proc/<pid>/cmdline`" (`M/sdk/rust/lib/runtime/spawn.rs:551-553,1469-1482`) | **Yes, both.** Local catalog (`0700`/`0600`, not encrypted; `M/docs/security/secrets.mdx`, "Local catalog permissions"). Remote: sent as `env` in the create body (`M/packages/microsandbox-types/rust/lib/cloud/mod.rs:616`) | **Yes, both.** `config()` returns `Env []{Key, Value}` (`M/sdk/go/core/config_inspection.go:24,69-73`). Only secret values and mount sources are redacted (`M/sdk/rust/lib/sandbox/config_inspection.rs:259-268`). The v0.8 notes list "environment" in the remote view (`M/docs/migrations/v0.8.mdx:142`) |
| **File** (`FS().Write`, or `WithPatches` before boot) | No | Lands in the per-sandbox writable layer on disk until the sandbox is removed (`M/docs/security/filesystem.mdx:23`). Patches are part of the persisted spec (`M/sdk/go/core/config_inspection.go:31`) | Patches: yes. Written files: no |
| **msb secret** (`WithSecrets`, `M/sdk/go/core/options.go:1069,1511`) | No | Raw values "persisted in the host-side sandbox configuration; stopping the sandbox does not remove that copy" (`M/docs/security/secrets.mdx:57`). Remote: sent to the cloud, which stores it in a vault ("OpenBao vault path is never exposed", OpenAPI `SandboxSecretResponse`) | Value redacted |

- **msb secrets don't fit the JIT config.** The guest only ever holds a placeholder that the host proxy swaps into HTTP requests to allowed hosts over intercepted TLS (`M/docs/security/secrets.mdx:9-25`). "Guest-side signing: A placeholder cannot replace raw credentials used to sign requests inside the guest." (`M/docs/sandboxes/secrets.mdx:905`). **(inferred)** The runner decodes the JIT config locally and uses the key in it to authenticate, so a placeholder can't work.
- **Inside the guest nothing is hidden.** The job runs in the same VM as the listener, with passwordless sudo, so it can read the listener's argv, env and files **(inferred)**. That is acceptable because the config is single-use: "These self-hosted runners perform at most one job before being automatically removed" (`GH:actions/reference/security/secure-use`). GitHub's warning about secrets on command lines leaking via `ps x -w` is about one runner running several jobs (same section).
- **Conclusion (inferred):** stdin is the channel with the smallest footprint on both Backends: no argv, no persisted spec, no `config()` exposure. `WithEnv` is the worst. It persists the config in the local catalog and in the cloud spec, readable by anyone with the profile's API key until the sandbox is removed.
- **Remote, any channel:** the config crosses the cloud API (TLS to the msb cloud), and the cloud operator can see it. Whether exec input is logged server-side is not documented.

## 3. Image provenance

### 3.1 What msb does

- **Pull by digest: yes.** `WithImage` takes any OCI reference, parsed with `oci_client::Reference`. After fetching the manifest, msb compares it with the reference's digest and fails with `ImageError::DigestMismatch` on a difference (`M/crates/image/lib/registry/client.rs:665-675`). Each uncompressed layer is checked against the config's `diff_id` ("the OCI content trust check"; `M/crates/image/lib/registry/client.rs:1223-1233`).
- **Signatures and attestations: no.** No signature, cosign, Sigstore or in-toto verification exists in the image crate or the Go SDK. When resolving a multi-arch index, entries whose media type contains `attestation` are skipped (`M/crates/image/lib/registry/client.rs:881-883`). **(inferred)** buildx's attestation manifests in our index are therefore harmless.
- **Remote:** the reference and `pull_policy` go to the cloud as-is (#3), and the pull happens server-side. **(inferred)** The cloud runs the same image crate, so the digest check applies there too, but this is not stated.
- **Local cache:** "Once microsandbox resolves an image reference, it pins the exact layers" (`M/docs/images/overview.mdx:60`). With `if-missing`, a cached digest reference is safe to reuse, because the digest names the content.

### 3.2 What GitHub offers for a GHCR image from CI

- **Attestations.** `actions/attest` with `subject-name: ghcr.io/<owner>/<image>` (no tag), `subject-digest: sha256:…` (e.g. `docker/build-push-action`'s `digest` output) and `push-to-registry: true`. Permissions: `id-token: write`, `contents: read`, `attestations: write`, `packages: write` (`GH:actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations`). The result is a Sigstore-signed SLSA provenance statement. Public repositories use the Sigstore Public Good Instance with a public transparency log. Attestations alone give SLSA v1.0 Build L2; a reusable workflow gives L3 (`GH:actions/concepts/security/artifact-attestations`). Available for public repos on all current plans (attest-build-provenance README).
- **`actions/attest-build-provenance` is now a wrapper.** "As of version 4, `actions/attest-build-provenance` is simply a wrapper on top of `actions/attest` … new implementations should use `actions/attest` instead." (attest-build-provenance README). The GitHub docs already use `actions/attest@v4`.
- **REST:** `GET /repos/{owner}/{repo}/attestations/{subject_digest}` lists bundles. It needs read access to the repo, and the docs warn that the signature, timestamps and signer identity must be verified, pointing at `gh attestation verify` (`GH:rest/repos/attestations`).
- **`gh attestation verify oci://<image>`** checks the bundle against the SLSA v1 predicate by default. It requires `--owner` or `--repo`, and recommends `--signer-workflow` (or `--cert-identity`) to pin the workflow. It also has `--source-ref`, `--source-digest` and `--deny-self-hosted-runners`. "If you provide an OCI URL, you must already be authenticated with its container registry". By default it fetches bundles from the GitHub API, or from the registry with `--bundle-from-oci`. `--format json` prints the verified result (gh manual).
- **cosign:** not covered by any of the GitHub pages read here. It would be a new external binary; not investigated further.

### 3.3 Can the Pool verify at start without new dependencies?

**(inferred)** Yes, by shelling out to `gh`, which every gh extension already has:

1. Resolve the contract tag to a digest with plain `net/http`. GHCR issues anonymous pull tokens for public packages. Live check: `GET https://ghcr.io/token?scope=repository:actions/actions-runner:pull`, then `HEAD /v2/actions/actions-runner/manifests/latest` with an OCI-index `Accept`, returned `200`, `content-type: application/vnd.oci.image.index.v1+json` and a `docker-content-digest`. `ghcr.io/arteven/gh-runners-msb` returns `DENIED` today because the package doesn't exist yet (`gh api users/arteven/packages/container/gh-runners-msb` → 404).
2. `gh attestation verify oci://ghcr.io/arteven/gh-runners-msb@sha256:<index> --repo arteven/gh-runners-msb --signer-workflow arteven/gh-runners-msb/.github/workflows/<image workflow>.yml` (optionally `--deny-self-hosted-runners`, `--source-ref refs/heads/master`).
3. Create every Runner from `ghcr.io/arteven/gh-runners-msb@sha256:<index>`. msb then enforces that exact content on local, and probably on remote.

Notes:

- The attestation's subject must be the **index** digest that `docker/build-push-action` outputs for a multi-arch push, so that steps 1–3 all talk about the same digest **(inferred)**.
- This also gives #9 its "refresh once at Pool start" mechanism: the digest lookup *is* the refresh, and every Runner in the Pool uses one pinned digest.
- It needs network access to the GitHub API and Sigstore's trust root. Whether `gh` fetches the trust root on every run or caches it was not checked.
- It needs a gh version that ships `gh attestation`; the exact minimum version was not checked.
- Doing the same in-process would need sigstore-go, which is a new dependency.
- `--image` (user-managed, maybe `msb load`ed under `localhost/…`) can't be verified this way and should skip the check.

## 4. GitHub guidance that affects a Pool

- **Public repositories:** "self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment." Self-hosted runners "can be persistently compromised by untrusted code in a workflow" (`GH:actions/reference/security/secure-use`, "Hardening for self-hosted runners"). The runner-groups page repeats: "We recommend that you only use self-hosted runners with private repositories" (`GH:actions/how-tos/manage-runners/self-hosted-runners/manage-access`).
- **Approval is not a security boundary for self-hosted runners.** "If you are using self-hosted runners, potentially malicious user-controlled workflow code will execute automatically if the user is allowed to bypass approval in the set approval policy or if the pull request is approved." The default is that only first-time contributors need approval, and "a user that has had any commit or pull request merged into the repository will not require approval". `pull_request_target` workflows "will always run, regardless of approval settings" (`GH:repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository`, "Controlling changes from forks…").
- **The setting is readable by the Pool:** `GET /repos/{owner}/{repo}/actions/permissions/fork-pr-contributor-approval` → `approval_policy` ∈ `first_time_contributors_new_to_github`, `first_time_contributors`, `all_external_contributors` (`GH:rest/actions/permissions`). Live, with gh's token: this repo is `public` and returns `{"approval_policy":"first_time_contributors"}`, the default.
- **Fork PRs get no secrets:** "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository. The `GITHUB_TOKEN` has read-only permissions" (`GH:actions/reference/workflows-and-actions/events-that-trigger-workflows`). Dependabot PRs are treated the same. **(inferred)** On a Pool, the remaining risk from a fork PR is the Runner's own reach: network egress, the cloud metadata service, the host and LAN. That is exactly what §1 controls.
- **Ephemeral / JIT is the recommended shape.** "GitHub recommends implementing autoscaling with ephemeral self-hosted runners". The Pool should forward runner logs externally: "The runner application log files for ephemeral runners must be forwarded to an external log storage solution". "Re-using hardware to host JIT runners can risk exposing information from the environment. Use automation to ensure the JIT runner uses a clean environment." (`GH:actions/reference/runners/self-hosted-runners`, "Ephemeral runners for autoscaling"; `GH:actions/reference/security/secure-use`). One fresh VM per job meets the last point **(inferred)**.
- **Machine hygiene:** GitHub asks "Does the machine have network access to sensitive services? For example, Azure or AWS metadata services." (`GH:actions/reference/security/secure-use`). That maps to msb's metadata and private-range defaults.
- **Runner groups:** "By default, only private repositories can access runners in a runner group" applies to organization runner groups (`GH:actions/how-tos/manage-runners/self-hosted-runners/manage-access`). **(inferred)** It does not gate the Pool's repository-level runners (group 1, #7).

## Unknowns

1. **Remote default network policy.** What the cloud applies when `policy` is null, and which deployment profile its hosting driver uses. A probe from an ephemeral remote sandbox (`curl` to a public host, an RFC 1918 address, `169.254.169.254`, the gateway) would settle it.
2. **Remote metadata endpoint.** Whether anything answers on `169.254.169.254`, or on a provider-specific address, on a cloud worker. The cloud's hosting provider is not documented.
3. **Remote DNS.** Resolvers, rebind protection and whether `DNSConfig` fields are silently dropped (the code suggests they are).
4. **Remote cross-tenant isolation.** Whether sandboxes on one worker, or in one org, can reach each other.
5. **Remote exec input retention.** Whether the cloud logs exec args, env or stdin.
6. **Remote digest enforcement.** Whether the cloud's pull checks `@sha256:` the way local does.
7. **`gh attestation verify` operational details.** The minimum gh version; trust-root fetching and caching; whether `oci://` on a public GHCR image works with no Docker credentials.
8. **Hostname policy under `DisableStrict`** with GitHub's CNAME-heavy domains (`*.actions.githubusercontent.com`, `*.blob.core.windows.net`). Untested.
